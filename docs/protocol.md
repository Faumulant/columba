# Columba 协议 v1

任何平台按本文实现即可成为 Columba 设备。本文件是平台无关的唯一契约；
当前版本 `proto = 1`。核心原则：只依赖标准件（UDP 组播、TLS 1.3、HTTP 语义），
应用层消息保持最少。

## 1. 设备身份

- 每台设备首次运行时生成 Ed25519 密钥对与一张 10 年期自签证书
  （CN = 设备名，ExtKeyUsage 同时允许 ServerAuth / ClientAuth）。
- **设备 ID = 证书 DER 的 SHA-256**，64 位大写 hex；显示时按 8 字符分组：
  `<设备指纹前缀>-D970E014-…`。
- 重建身份 = 更换设备 ID，所有信任关系随之失效（这是预期行为）。

## 2. 发现（UDP 组播）

- 组播组 `224.0.0.240:42708`，TTL=1，不出本网段。
- 每台设备每 2 秒广播一条 JSON `Announce`：

  ```json
  {"proto": 1, "id": "<设备指纹前缀>…64位HEX…", "name": "我的电脑", "port": 42707}
  ```

- 宣告通过**所有已加入组播组的有 IPv4 地址的非回环网卡**发送
  （规避 Windows 上 VPN/虚拟网卡劫持默认组播路由的问题）。
- 收到宣告即得到：对端 IP（来源地址）+ TCP 端口（负载内）。
- 宣告不携带认证；ID 的真实性由 TLS 握手校验（见下节）。
- 实现注意：接收端应加入**所有**候选网卡的组播组（同上），而非仅系统默认网卡。

## 3. 会话加密与认证

- 所有端点跑在 **TLS 1.3 + 客户端证书（mTLS）** 之上。
  认证（证书）在握手层，授权（信任）在应用层。
- 双方均按证书指纹互认，不使用 CA 链：
  - 客户端把目标设备 ID（来自宣告或用户指定）作为 pin：对端证书指纹不符即断开；
  - 服务端按端点分级授权：`/v1/pair` 对任何持证书对端开放；
    其余端点要求已配对，否则 401。
- 配对码仅作一次性带外授权凭证，**绝不参与密钥派生**。

## 3.5 配对（一次性识别码）

1. 一方 `drop pair`：生成 6 位数字配对码，5 分钟有效，进入等待；
2. 另一方 `drop pair <码>`：经发现/直连连到对方，提交 `{code, name}`；
3. 服务端常量时间比对配对码；**无论后续是否确认，码立即失效**；
4. 服务端向本机用户展示对方名称与指纹，人工确认（y/n）；
5. 确认后双方把对方证书写入各自信任库 → 数据端点互相放行，
   直到任一侧手动移除信任；未确认则双方都不入库。

## 4. 传输（HTTPS 端点）

| 端点 | 请求体 | 响应 |
|---|---|---|
| `POST /v1/offer` | `Offer`（JSON） | `OfferAck`：`session_id` 非空即接受，`message` 非空即拒绝原因 |
| `POST /v1/upload?s=&f=` | 文件原始字节流 | 200 继续；4xx/5xx 终止 |
| `POST /v1/complete` | `CompleteReq`（JSON） | `CompleteAck`：`ok=true` 表示校验通过、已落盘 |
| `POST /v1/pair` | `PairReq`（JSON） | `PairAck`：`ok=true` 表示对方确认，双方互写信任库 |
| `POST /v1/text` | `TextMsg`（JSON） | 200 表示已入历史（文本不落盘） |
| `POST /v1/unlock` | `UnlockMsg`（JSON） | `UnlockAck`：`ok=true` 表示已记录 |

```json
Offer     {"proto":1,"session_id":"","sender_id":"…","sender_name":"…",
           "files":[{"id":"f0","path":"dir/子目录/a.txt","size":123}],
           "total_size":456}
OfferAck  {"session_id":"…","message":""}
CompleteReq {"session_id":"…","file_id":"f0","sha256":"…","bytes":123}
CompleteAck {"ok":true,"saved_as":"dir/子目录/a.txt","message":""}
UnlockMsg {"proto":1,"unlocked":true}
UnlockAck {"ok":true}
```

- `files[].path` 恒为 `'/'` 分隔的**相对路径**（多文件/文件夹保留目录结构）。
  服务端必须拒绝绝对路径、`..`、盘符等非法路径。
- `Content-Length` 必须等于清单中的 `size`；不一致立即失败。
- 上传端点串行化同一 `file_id`，并发上传同一文件返回 409。

### 4.1 解锁状态同步（`/v1/unlock`）

「设备数量上限」是产品层的一次性解锁（用户点一次即永久生效）。解锁状态通过本端点
在**已配对设备之间**互通，使「在任意一端点过，其余设备自动跟随」。

- 授权门槛与其余数据端点一致：**只对已配对设备开放**，未配对一律 401。
  这是硬要求——否则局域网内任意设备都能把上限刷开。
- 只同步 `unlocked=true`。收到 `false` 不做任何事：解锁是一次性用户决定，
  不支持远程撤销，避免一台设备误发就把已解锁状态抹掉。
- 收到 `true` 后接收端写本机解锁标记；已解锁时重复推送幂等，无副作用。
- 推送失败（对端离线/未启动）不影响本机解锁结果。

## 5. 完整性与落盘

1. 接收端把字节流写入 `<path>.part`，同时计算 SHA-256；
2. 发送端同样边读边算，在 `complete` 中上报哈希；
3. 双方一致 → 处理同名冲突（`photo.jpg` → `photo (1).jpg`，绝不覆盖）→
   同卷原子改名；不一致 → 删除 `.part`；
4. 连接中断 → 删除 `.part`，残缺文件不得伪装为成功；
5. 双方各自记录本地历史（成功/失败都记录）。

## 6. 版本化

- 所有消息携带 `proto` 字段；不兼容变更必须递增 major 并协商。
- 端口与组播地址为常量，但宣告内的 `port` 允许设备自行指定实际 TCP 端口。
